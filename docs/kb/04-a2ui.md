# A2UI — Agent-Generated UI

A2UI is how a model emits cre8 UI as **data** instead of as code. The agent
produces JSON; a renderer validates it against a catalog and builds real DOM. No
generated JavaScript is executed, which is the entire point.

Three things make up the system:

| Piece | File | Role |
|---|---|---|
| **Catalog** | `a2ui/catalog.json` | JSON Schema 2020-12 describing every component's props, enums, slots, events |
| **Registry** | `a2ui/registry.ts` | `registerCatalog()` and `validateSpec()` — the gate |
| **Renderer** | `a2ui/renderer.ts` | `render()` — turns a validated spec into DOM |

## The cre8 dialect

A spec is a **nested tree**. One node:

```ts
interface ComponentSpec {
  component: string;                          // tag name, must exist in the catalog
  props?: Record<string, unknown>;            // must be declared props
  children?: (ComponentSpec | string)[];      // default-slot content
  slots?: Record<string, (ComponentSpec | string)[]>;  // named slots
  events?: Record<string, string | { handler: string; stopPropagation?: boolean; preventDefault?: boolean }>;
}
```

A minimal real example:

```json
{
  "component": "cre8-card",
  "slots": {
    "header": [
      { "component": "cre8-heading",
        "props": { "tagVariant": "h3", "type": "title-default" },
        "children": ["Monthly plan"] }
    ],
    "default": [
      { "component": "cre8-text-passage", "children": ["Everything in Basic, plus priority support."] }
    ],
    "footer": [
      { "component": "cre8-button",
        "props": { "text": "Upgrade", "variant": "primary" },
        "events": { "click": "upgrade-clicked" } }
    ]
  }
}
```

*(This spec is verified — it passes `validateSpec` against the shipped catalog.)*

Four things to notice, because each is a rule:

1. **Props use camelCase**, matching the component's TypeScript property names
   (`tagVariant`, not `tag-variant`). The renderer decides attribute-vs-property
   at apply time.
2. **`cre8-card` takes its body through `slots.default`, not `children`.** This
   is not a stylistic choice — `children` on a card is a validation error. The
   rule is in [Children vs slots: the rule that breaks specs](#children-vs-slots-the-rule-that-breaks-specs), and it is the
   single most common reason a generated spec fails.
3. **Plain strings are text nodes.** In a named slot they get wrapped in a
   `<span slot="…">` automatically, which is the correct markup and saves the
   agent from getting it wrong.
4. **Event values are handler *names*, never code.** See
   [Events and the return path](#events-and-the-return-path).

## Children vs slots: the rule that breaks specs

In the catalog, **every component accepts content through either `children` or
`slots` — never both.** Passing the wrong one is a hard validation error with a
message like `cre8-card does not accept default children`.

| Bucket | Count | How to pass content |
|---|---|---|
| Children-only | 47 | `"children": [...]`; `slots` is an error |
| Slot-only | 25 | `"slots": { "default": [...] }`; `children` is an error |
| Leaf | 13 | Neither — content comes from props (`text`, `iconName`, `data`) |
| Both | 0 | The catalog never does this |

The split does not follow from a component's name or purpose, so it cannot be
guessed. `cre8-heading` and `cre8-text-passage` are children-only; `cre8-card`,
`cre8-button`, `cre8-modal`, `cre8-field`, and `cre8-table-row` are slot-only;
`cre8-badge` and `cre8-icon` are leaves. The full generated lists are in
[`reference/content-model.md`](reference/content-model.md).

**And a third case:** 6 of the 25 slot-only components declare no `default` slot
at all — `cre8-button`, `cre8-field`, `cre8-select`, `cre8-multi-select`,
`cre8-date-picker`, `cre8-checkbox-field-item`. They accept no free content in
any form. `cre8-button`'s label is the `text` prop:

```json
{ "component": "cre8-button", "props": { "text": "Upgrade", "variant": "primary" } }
```

Not `children: ["Upgrade"]`, and not `slots: {"default": ["Upgrade"]}` — both are
validation errors. This is the most common single mistake in generated specs,
because every other UI system in existence puts button labels between the tags.

Two practical consequences:

- **`slots.default` and `children` are not interchangeable.** The renderer treats
  the `"default"` slot key as the default slot (it omits the `slot` attribute),
  so they produce identical DOM — but the *validator* accepts only the one the
  catalog declares.
- **HTML intuition does not transfer.** In hand-written HTML you nest cell
  elements inside `<cre8-table-row>` and it works. In A2UI, `cre8-table-row` is
  slot-only, so the same structure must be `"slots": { "default": [...] }`.

> This asymmetry is a catalog modeling decision, not a component constraint —
> `cre8-table-body` is children-only while its child `cre8-table-row` is
> slot-only, which is why table specs are the most error-prone thing to generate.
> Worth revisiting upstream; until then, check
> [`reference/content-model.md`](reference/content-model.md) before emitting a
> container.

Four complete worked specs live in `a2ui/examples/`: `portfolio.json`,
`card-gallery.json`, `dating-grid.json`, `llm-observability.json`. All four
validate against the shipped catalog; `llm-observability.json` needed two
corrections to get there. See [Worked examples](02-composition-patterns.md#worked-examples).

→ *If you want the composition rules these specs must obey, see
[Composition Patterns](02-composition-patterns.md) — validation checks structure, not taste.*

## Validation

`validateSpec(spec, catalog)` throws on the first problem with a path-qualified
message like `$.slots.body[0].props.variant: value "bogus" not in enum ["primary", …]`.
It is strict by design, and it enforces:

- **Component allowlist** — the tag must exist in the catalog.
- **Prop allowlist** — an undeclared prop is an error, not a pass-through. This is
  the check that catches hallucinated APIs.
- **Value constraints** — `const`, `enum`, `oneOf`, type, array `items`, nested
  object `properties` / `required`, and `additionalProperties: false`.
- **Children legality** — `children` on a component that does not declare them is
  an error.
- **Slot names** — an undeclared slot name is an error.
- **Event binding shape** — a string, or an object with a non-empty `handler`.

`render()` calls `validateSpec()` first, so you cannot render an invalid tree by
accident. Validate separately when you want to check without a DOM — in a
server-side agent loop, in CI, or in a test.

From an agent, the same check is available as the MCP tool **`validate_a2ui_spec`**,
which returns `{ ok: true }` or `{ ok: false, error }`. An agent that generates a
spec and does not call this before returning it is skipping the one cheap step
that catches most of its own mistakes.

### What validation cannot catch

Validation is only as good as the catalog, and the catalog is generated — partly
from component sources, partly from a **hand-maintained override table**
(`PROP_OVERRIDES`) at the top of `a2ui/generate-catalog.mjs`. Where that table is
wrong, the validator confidently blesses invalid output.

**Worked example (now fixed, kept because the shape recurs).** `cre8-heading.type`
was overridden with a hardcoded enum listing `"label"`, while the component's
TypeScript union and its `render()` mapping both used `"label-default"`. The
consequence chain:

1. An agent reads the catalog and sees `"label"` is a legal value.
2. It emits `{"props": {"type": "label"}}`.
3. `validate_a2ui_spec` **passes** — the value is in the enum.
4. The renderer sets `type="label"`.
5. No class matches in `heading.ts`, *and* a truthy `type` suppresses the
   `tagVariant` size fallback — so the heading renders with **no size class at
   all**.

A silently unstyled heading, from a spec that validated cleanly. Fixed by
correcting the override to `label-default` and regenerating.

The general lesson outlives the bug: **a green validation result means
"consistent with the catalog," not "correct."** When catalog and implementation
disagree, validation launders the error instead of catching it.

The durable fix is structural, and it is now the house rule in
`generate-catalog.mjs`: **add a `PROP_OVERRIDES` entry only when the manifest
type is genuinely unresolvable** — an interface name, an imported alias, or a
union TypeScript truncated with `... N more ...`. Anything the generator can
already derive should be derived, because a hand-maintained schema entry is prose
wearing a schema's clothing and drifts exactly like prose. Every remaining
override is a standing liability; audit them when a component's API changes.

```js
import { registerCatalog, validateSpec, render } from '@tmorrow/cre8-wc/a2ui';
import catalog from '@tmorrow/cre8-wc/a2ui/catalog.json' with { type: 'json' };

const registered = registerCatalog(catalog);
validateSpec(spec, registered);                       // throws on bad input
render(spec, registered, { root: document.getElementById('app'), onEvent });
```

## How props actually reach the element

`applyProp` in the renderer resolves each prop in this order, and the order
explains most "why did my value not apply" questions:

1. `x-kind: "property"` in the catalog → set as a JS property.
2. Boolean → presence attribute (`true` sets `attr=""`, `false` removes it).
3. Array or object → set as a JS property (attributes cannot carry structured
   data).
4. A complex schema → set as a JS property.
5. Everything else → `setAttribute(key, String(value))`.

So a chart's `data` array becomes `el.data = [...]`, while `variant: "primary"`
becomes `variant="primary"`. Agents do not need to know which is which — that is
what the catalog's `x-kind` annotation is for.

## Events and the return path

Handlers are **names**, not functions and not code strings:

```json
{ "events": { "click": "upgrade-clicked" } }
```

or, with modifiers:

```json
{ "events": { "click": { "handler": "upgrade-clicked", "preventDefault": true } } }
```

The renderer attaches a listener that calls your single `onEvent` callback with:

```ts
{ component, path, event, handler, detail, nativeEvent }
```

`path` is the spec-tree location (`$.slots.footer[0]`), which is how you tell two
identical buttons apart without the agent inventing IDs.

This is the security boundary. A model that emits a spec cannot emit behavior —
it can only *name* an intention, and your application decides what that name does.
Treat handler names as an allowlist you own:

```js
const handlers = { 'upgrade-clicked': () => startCheckout() };

function onEvent({ handler, detail, path }) {
  const fn = handlers[handler];
  if (!fn) return console.warn('unknown handler', handler, 'at', path);
  fn(detail);
}
```

Never `eval` a handler name, never look it up in a global object you do not
control, and never let the spec supply the function body. The whole architecture
is worth nothing if you reintroduce code execution at the last step.

→ *For the broader question of what to trust from a model, see
[Diligence: owning the result](05-ai-fluency.md#diligence-owning-the-result).*

## Best practices

**For the agent producing specs**

1. **Read the catalog before generating, not after failing.** `get_a2ui_catalog`
   with `view: "metadata"` is cheap (names, categories, version); `view: "component"`
   for the one component you are about to use. Pull `view: "full"` only when you
   genuinely need the whole schema — it is large and usually wasted context.
2. **Validate every spec before returning it.** `validate_a2ui_spec`. The error
   message names the exact path and the allowed values, so a second attempt
   almost always succeeds.
3. **Prefer a declared prop over slotted markup.** `{"props": {"text": "Save"}}`
   beats slotting a text node when the prop exists — it is checkable and it
   survives component changes.
4. **Do not invent props to express layout.** Layout comes from composition
   (`cre8-grid`, `cre8-layout-section`), not from a `margin` prop that does not
   exist. The validator will reject it; more importantly, the design system has
   an answer already.
5. **Emit tag names, never React component names.** `cre8-button`, not
   `Cre8Button`. React output is a *rendering* concern — `generate_code` with
   `format: "react"` handles that translation.

**For the application hosting the renderer**

6. **Register the catalog once** and reuse the `RegisteredCatalog`;
   `registerCatalog` builds a Map on every call.
7. **Keep the handler allowlist small and explicit.** One object, named
   intentions, no dynamic lookup.
8. **Version-check the catalog against the installed library.** A spec validated
   against a catalog that is newer than your `@tmorrow/cre8-wc` will render
   components that do not exist.

**For whoever maintains the components**

9. **Regenerate after any API change** — `pnpm build:a2ui:catalog` writes the
   catalog from the component sources; `build:a2ui` and `build:a2ui:compile` cover
   the rest. A stale catalog does not fail loudly; it silently teaches every agent
   the wrong API.

## Keeping the A2UI artifacts in sync

Four artifacts carry independent version stamps: `package.json`,
`mcp-manifest.json`, `a2ui/catalog.json` (`$id` and `x-a2ui.libraryVersion`), and
`a2ui/catalog-kg.json` (`meta.library_version`). They currently agree at **2.0.7**.

They have disagreed before — the catalog sat at 2.0.6 and the knowledge graph at
2.0.4 while the package was 2.0.7 — with component counts matching at 85
throughout, so the symptom was a stale `$id` rather than missing components. That
matters because consumers reasonably treat `$id` as a cache key.

Regenerate them together (`pnpm build:a2ui:catalog` and the sibling `build:a2ui:*`
scripts) rather than individually, and check
[`reference/facts.json`](reference/facts.json) — `pnpm kb:generate` reads the
stamps straight from the artifacts, so a fresh divergence shows up there first.

## The catalog knowledge graph

`a2ui/catalog-kg.json` is a graph projection of the catalog — a few hundred nodes and edges, built by `a2ui/build-knowledge-graph.py`, visualized in `catalog.svg`.
Nodes are categories (`cat:Actions`) and components; edges are containment and
categorization relationships.

Its use is retrieval: given "the user wants a filter chip," a graph walk from the
Data category reaches `cre8-tag-list` → `cre8-remove-tag` without the model
reading 85 component definitions. It complements the flat catalog rather than
replacing it — the catalog is for validation, the graph is for navigation.

→ *This is the same idea as the intent index behind this KB; see
[`reference/intents.json`](reference/intents.json).*

## Conformance with a2ui.org v1.0

**cre8's A2UI is a related but distinct dialect from the published A2UI protocol.**
Say so plainly when interoperability comes up, because the names match and the
shapes do not.

| Dimension | a2ui.org v1.0 | cre8 A2UI |
|---|---|---|
| Tree shape | Flat adjacency list; parents reference children by `id` | Nested tree; children are inline objects |
| Node identity | `id` required per component | No ids; position path (`$.slots.footer[0]`) identifies nodes |
| Transport | Streamed messages: `createSurface`, `updateComponents`, `updateDataModel`, `deleteSurface` | Single spec object, rendered in one pass |
| State | Separate `dataModel`, bound by JSON Pointer (RFC 6901) | No data model; values are inline in `props` |
| Updates | Incremental, per-surface | Re-render |
| Catalog | `catalogId`, `"component": {"const": …}`, restricted `$defs` | `x-a2ui.catalogId`, `"component": {"const": …}`, `$defs.components` |
| Actions | `actionResponse` / `callFunction` RPC | `onEvent` callback with named handlers |

The catalog conventions line up closely — `catalogId`, the `const` discriminator
on `component`, per-component schemas. The **document model does not**: flat plus
data-binding versus nested plus inline values.

What this means in practice:

- A cre8 spec is **not** a valid a2ui.org `updateComponents` payload, and vice
  versa. A converter is mechanical but has to be written.
- cre8's model is simpler and a better fit for one-shot page generation.
  a2ui.org's model is built for **streaming and incremental update** — an agent
  progressively revealing UI, or patching one field without resending the tree.
- If cre8 ever needs streaming or agent-driven partial updates, adopting the
  flat+`id`+`dataModel` shape is the migration, and it is a breaking change to
  every spec and both renderers. Better to decide deliberately than to drift into
  it.
